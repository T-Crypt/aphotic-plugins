# OpenRGB Sync

Syncs [Aphotic-Hypr](https://github.com/T-Crypt/aphotic-hypr)'s active
theme accent to your RGB PC lighting through
[OpenRGB](https://openrgb.org/)'s SDK, and changes what the lighting is
doing when the Gaming profile activates or an AI agent session is live.

## What it does

| Trigger | Lighting |
|---|---|
| Theme / wallpaper change | Flat static accent (`color4`) across every detected device |
| Gaming profile activates | Same hue at full saturation, static |
| Gaming profile deactivates | Back to the idle theme color |
| An agent session starts working | Breathing, same theme accent |
| The last agent session stops | Back to static |

Those three inputs don't fight each other. Each one only records a fact,
and the lighting is always the resolution of all three —
`profile > agent > idle theme` — so a theme change mid-game doesn't
quietly undo game mode, and an agent going idle doesn't clobber it
either.

## Requires

- OpenRGB with its **SDK server** running (port 6742) — `openrgb --server`,
  or "Enable SDK Server" in the GUI's Settings tab.
- `python3` and the [`openrgb-python`](https://pypi.org/project/openrgb-python/)
  SDK client.
- `jq` (used by `scripts/setup.sh` only, not on the hook path).
- On Linux, a **udev rules file** for device access — see below. This is
  the single most common reason for "it connects fine and nothing
  happens".

## Install

```sh
git clone https://github.com/T-Crypt/aphotic-plugins ~/aphotic-plugins
aphotic plugin install openrgb
~/.local/share/aphotic/plugins/openrgb/scripts/setup.sh   # once
```

Or for plugin development (edits take effect without reinstalling):

```sh
aphotic plugin install openrgb --link
```

`setup.sh` is a separate, manual step because the plugin contract has no
post-install hook yet, and because everything it does needs either your
password or a decision only you can make. It checks the SDK client, the
udev rules, the I2C/SMBus module for DRAM RGB, and walks you through
sizing any hub channel that reports 0 LEDs. Re-run it whenever your RGB
hardware changes.

### Device access (udev) — read this first

Without `60-openrgb.rules`, the kernel denies your user access to the
hidraw/i2c nodes your RGB controllers live on. OpenRGB still starts, and
its SDK server still accepts connections perfectly happily — it just
enumerates **zero devices**, or fails every write. Nothing about that
looks like a permission problem from the outside, which is exactly why
this plugin treats it as a named, one-time setup condition instead of a
connection failure to retry:

- `scripts/setup.sh` checks for the rules file and, if it's missing,
  offers to install it — printing the exact `install` /
  `udevadm control --reload-rules` / `udevadm trigger` commands first and
  waiting for an explicit `y/N`. It never silently `sudo`s anything, the
  same confirmation-gated posture the rest of Aphotic uses for
  elevated-trust tooling.
- The hooks themselves detect the symptom (a successful connection with
  zero devices, or every device erroring on write, with no rules file
  present) and raise **one** desktop notification pointing back at
  `setup.sh` — once per distinct condition, not once per wallpaper
  change.

The rules file is copied from whatever your OpenRGB install shipped, or
generated by OpenRGB itself where that's supported; it's a long
vendor/device table that goes stale, so this plugin doesn't carry its own
copy. Note it's a *rules file*, not a reason to run OpenRGB as root —
running it elevated papers over the problem and hands a GUI app more
privilege than it needs.

## Why dominant-color-only, for now

Every device gets one flat color derived from a single palette slot. No
per-device colors, no per-zone mapping, no manual override UI. That's a
deliberate scoping call, not an oversight:

- **A per-zone map has to be hand-built per machine, and this plugin has
  to work on machines nobody has seen.** Zone counts, names and ordering
  are vendor- and firmware-specific. The Windows automation this port
  came from was one-PC-specific for exactly this reason — its device
  table named that machine's exact GPU, fan hub and PSU cables. Anything
  richer than "one color everywhere" needs a device-mapping UI to be
  usable by anyone else, and that UI is a bigger piece of work than the
  sync layer it would sit on top of.
- **The mechanism has to be proven before the presentation is.** The hard
  part of this port is per-device isolated writes and `color_mode`-aware
  application (below) — being correct about *how* a color reaches a
  device. Layering zone mapping on top of a write path that isn't yet
  trusted on arbitrary hardware would just make failures harder to
  attribute.
- **The palette only really names one accent.** `color4` is the slot the
  shell itself maps to its `m3primary` role. Which slot counts as "the
  accent" is still an open question in the plugin system's own design doc
  (`PLUGIN_SYSTEM.md` §5); this follows the shell rather than deciding it
  independently, and a per-zone scheme would need several such decisions
  instead of one.

Per-zone/per-device customization is real, useful follow-up work. It
wants its own pass, with a mapping UI, once this layer has run on more
than one rig.

## How it applies color (the part worth not rewriting)

`lib/rgb_common.py` is ported from a standalone Windows OpenRGB project
whose value was everything it got empirically wrong first, against a real
mixed rig. Two behaviours carried over unchanged:

- **Per-device isolated writes.** Each device's mode+color write is in its
  own `try`/`except`, and the per-device outcome is returned rather than
  swallowed. Without that, one transient failure — HID controllers are
  prone to it, unlike I2C-attached GPUs and DRAM — aborts the batch and
  silently skips every device after it, which reads as "that one device
  is stuck" rather than as the ordering bug it is.
- **`color_mode`-aware application.** Every OpenRGB mode declares
  `NONE`, `PER_LED` or `MODE_SPECIFIC`, and they are not interchangeable.
  `MODE_SPECIFIC` devices read their color from the mode packet, not the
  LED buffer. `PER_LED` devices need a zone-by-zone write, since a flat
  device-wide one doesn't reliably reach every populated zone. `NONE`
  modes are self-driven and take no color at all — writing LED bytes over
  one fights the running effect. A `--mode Static --color <hex>` CLI call,
  which is what this plugin used to do, assumes exactly one of those three
  cases.

What did **not** carry over is every hardcoded device name. The original
kept a device list and an effect→mode table naming that machine's exact
hardware. Here the same decision is made at runtime: `resolve_mode()`
walks a preference list of mode names and takes the first one the device
actually has *that can accept a color*, falling back to the static
resolution when a device has no colorable breathing-style mode. That
runtime fallback reproduces, on any hardware, what the original had to
hardcode for its fan hub.

Also carried over: zone sizes are reasserted on every apply and compared
with `!=`, not `== 0`. A hub channel can come back from an OpenRGB
restart at a stale nonzero size, which a zero-check silently skips —
leaving lighting partial and off-hue with nothing reporting a problem.

## What core still has to wire

`theme-hook` is fired by core today. The other two capabilities in
`plugin.toml` use the same manifest shape and the same fire-and-forget
contract, but **nothing in the shell dispatches them yet** — they need
one call site each, alongside the existing `_aphotic_plugin_run_project_hooks`
/ `_aphotic_plugin_run_workspace_hooks` pair in `cmd_plugin.sh`:

- `profile-hook` → `on_profile_activate` / `on_profile_deactivate`, one
  positional arg (the ProfileEngine profile id, e.g. `gaming`), fired from
  `ProfileEngine`'s APPLY and RESTORE phases.
- `agent-event-hook` → `on_agent_event`, event JSON on stdin, fired from
  the same pipeline that already writes `agent-events.jsonl`. Named
  distinctly from the existing `harness-hook` capability on purpose:
  `harness-hook` wires an external harness's config *into* Aphotic,
  this consumes the events that come back out.

Until those land, both hooks are runnable by hand — which is also how to
test them:

```sh
scripts/rgb_sync.py profile activate gaming
scripts/rgb_sync.py profile deactivate gaming
echo '{"sessionId":"test","event":"session_start","harness":"claude"}' | scripts/rgb_sync.py agent-event
echo '{"sessionId":"test","event":"stop","harness":"claude"}'          | scripts/rgb_sync.py agent-event
```

## Tests

```sh
tests/run_tests.sh
```

Runs the real hooks against `tests/stub/`, a stand-in for
`openrgb-python` modelling the five controller shapes that produced the
bugs this port carries the fixes for — no OpenRGB, no SDK server, no RGB
hardware. It exists because the mode-resolution rules below encode
lessons learned on one specific rig and now re-derive them at runtime:
the test pins each resolution the original hardcoded, so a change to the
preference lists can't quietly undo one.

## Troubleshooting

Everything the hooks do lands in
`~/.local/state/aphotic-plugins/openrgb/sync.log`, including per-device
`ERROR`/`SKIP` lines and the reason a connection failed. Nothing on the
hook path ends in `|| true`.

```sh
scripts/rgb_sync.py status    # what's ACTUALLY applied per device, read back from OpenRGB
scripts/rgb_sync.py devices   # full inventory: zones, LED counts, resolved modes
scripts/rgb_sync.py apply     # force-reapply the current resolved state
tail -f ~/.local/state/aphotic-plugins/openrgb/sync.log
```

`status` reads back the live mode and color from OpenRGB rather than
reporting what was last requested — the two disagree exactly when
something went wrong, which is when you're looking.

## Configuration

`~/.config/aphotic-plugins/openrgb/settings.conf` (created on first run
from `config/settings.conf.example`) covers the accent override, device
exclusions, the idle/gaming/agent effects, the Gaming saturation floor,
which profile ids and harnesses to react to, and the SDK host/port.
`zones.conf` holds hub channel LED counts, written for you by
`setup.sh`.
